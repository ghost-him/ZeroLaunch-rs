# 工程纪律（粘性规则 — 始终生效）

## 死代码纪律

- 无用代码立即删除；Git 历史是唯一备份。NEVER 创建或提交 `.bak`、`.copy`、`.old`、`_backup`、`lib copy.rs` 类副本文件（TTSR 规则亦在写入瞬间拦截）。
- `// temp`、`// 临时`、`// 待重构`、`// TODO: remove` 是当次会话内必须清掉的标记，NEVER 提交。

## 数据流纪律（KISS + 流程精简）

- 母原则：**每个事实只存在一次，且只移动必要的距离**。KISS 管静态形状（概念不重复、数量不超出必要），流程精简管动态路径（数据从产生点到消费点的每一跳都要买到东西）。度量单位是 **权威数 + 必要跨界数**，NEVER 是层数、文件长度或函数个数——把三层折进一个巨函数不是精简。删掉一个 hop 等于同时删掉一整类一致性 bug 及其校验代码。
- 概念预算（KISS 半部）：优先扩展现有抽象；NEVER 在现有架构能容纳需求时引入新的模块、trait 或层。重构前先确认变更放得进当前 plugin/pipeline/config 框架，只有现有抽象被证明无法容纳时才提出新抽象。
- 反模式名录（评审时指名）：隧道层、双重声明、影子副本、猜测翻译、中途有损表示、补偿同步、兼容夹层、拓扑镜像。

### 单一写者（单一权威）

- 每个事实（字段、状态、元数据、开关、计数）MUST 只有一个写入者或声明处。两个写者 = 两份真相 = 靠"同步"弥合 = 漂移 bug 与随之而来的一整堆一致性断言。
- 判据：假设两处给出不同值，你能立刻回答"谁赢"吗？答不出 → 权威重复，MUST 合并权威而不是补同步逻辑。出现 `sync_*` / `refresh_*` / `rebuild_*` / `fixup_*` 这类"以保持一致为职责"的函数即设计错误信号。
- 例：插件级元数据唯一声明处是 `manifest.toml`（宿主直读构造 `PluginMetadata`，协议无 `plugin/get_metadata`、`Plugin` trait 无 `metadata()`）；"清单声明一次 + 插件进程再上报一次"是反例。
- 代价：单一权威会让非权威方失去可见性 → 正解是给它**读接口**（host API），错解是给它一份拷贝（那会当场制造第二个权威）。

### 每一跳必须购买能力

- 数据从产生点到消费点之间，每个中间模块 / trait / RPC / DTO MUST 至少购买一项能力：**进程隔离、并发隔离、信任边界、序列化边界（协议版本闸门、崩溃隔离）、权限收敛**。一项都买不到的 hop 是隧道层，MUST 删除。
- 三问（任一答不上即删）：①它在这条数据上做了什么**决定**？②它**丢了什么信息**？③它是否制造了**新副本 / 第二权威**？
- 例：`plugin-host` 的进程边界买到了崩溃隔离与协议版本闸门；只把上游字段抄进自己的 DTO 再转交下游，是隧道层。
- 例外：跨进程边界不可删（序列化就是要买的那项能力）；不可信输入即使"能直读"也 MUST 过边界校验——这两处多一跳是买安全，不是弯绕。

### 声明即传输（已落盘的数据不搬运）

- 数据已经落在磁盘 / 配置 / DB 上时，MUST NOT 先搬到另一处再传回来；让消费方直读权威载体，或由持有方提供读接口。判据：这一跳传输的字节能否由两端已有数据推出？能 → 该 hop 冗余。
- 例：`manifest.toml` 是清单落点，宿主 `load_single_plugin` 直接解析；"插件 host 读清单 → RPC 上报宿主 → 宿主再校验一遍"是反例。宿主直读意味着元数据是**启动时快照**，改清单需重启生效——这是语义不是 bug。
- 例外：热路径允许缓存（内存 / 磁盘），但缓存即副本，MUST 在实现处说明**失效点与触发者**；答不出失效点的缓存按影子副本人处理。

### 派生数据可重算、不可复制

- 可由权威数据或同一 payload 其它字段算出的值，MUST NOT 传输或存储第二份，由消费方计算。判据：能否从同一 payload 的其它字段推出？能 → 不发、不存。
- 反例信号：DTO / 事件 / 配置里出现"方便下游"的冗余字段——上游一变它不会跟着变。正例：只下发原料（如关键词产物），分数由消费方算；错例：把计算结果塞进载荷并让下游信任它。
- 跨层载荷 MUST 与数据源同构，禁止启发式再解释（不得把真实事件猜成"安装 / 卸载"再下发）。

## 错误处理边界

- **该 `panic!` 就 `panic!`**：判据是问题成因——源于程序员（内部不变量被破坏、处理逻辑写错）→ 直接 `panic!`，让问题第一时间暴露、可被定位；与用户操作相关（非法输入、外部环境不可控）→ 在入口边界第一时间兜底（校验、降级、报错），兜底之后的内部链路不再兜底、出错即 panic。过度兜底会掩盖 bug，让问题难以发现。
- **防御性检查只在入口边界**：内部链路信任已建立的不变量；不为"契约保证不可能发生"的分支写兜底代码，不在每个调用点重复校验同一不变量——那会掩盖契约错误、拖慢热路径。
- **内部不变量用 `debug_assert!`**：开发与测试环境立即暴露，release 编译为零开销。不要因为"release 会被编译掉"就省略检查或改写成手写 `if`；也不要为这类条件引入带错误处理的运行时检查（那是把程序员错误当用户输入兜底）。仅当条件在 release 也必须成立且类型系统保证不了时，才用运行时检查。

## 前后端职责边界

- 前端只负责 **数据显示** 与 **用户交互**，是"薄"展示层：接收后端结构化数据 → 渲染 DOM → 收集用户输入 → 经 IPC 回传。NEVER 在前端实现业务逻辑、直接操作文件系统 / 启动程序 / 调用平台 API。
- **业务逻辑的判据是权威性**：产生权威数据、裁决路由 / 会话状态、持久化、调度平台操作的逻辑 MUST 在后端。涉及数据、文件、进程、网络的操作 MUST 经 IPC 委托后端；纯 UI 交互（主题切换动画、键盘导航、窗口尺寸）可放前端。
- 前端允许**展示层派生与输入交互层判定**（computed 派生、防抖豁免、在途提示）：仅影响展示与时序、不产生权威结果、随时可被后端响应推翻；此类判定若镜像后端解析规则，参数 MUST 取后端下发，镜像点 MUST 在注释中声明并随后端同步（细则见 TTSR 规则 `frontend-input-interaction`）。
- **正确**：前端调用 `bridge_query` 获取结果并渲染 / 调用 `bridge_confirm` 委托后端启动程序。**错误**：前端直接读文件系统拼候选列表 / 直接调 shell 或进程 API / 直接写剪贴板（须经 `bridge_confirm` → 后端 `PluginHandle::set_clipboard_text`）。

## 用户交互

- 需要用户决策时 MUST 使用 `ask` 工具；需求涉及实际代码改动时，MUST 先出计划待用户确认再改。

## 软件工程

- 新写的函数 MUST 前置一段精简的中文注释（功能、入参、返回、错误情况）。改动已有函数时校正其中过时的注释，NEVER 删除仍然正确的注释。

## 验证纪律

- 对可编译验证的问题（trait bound、Send/Sync、生命周期、编译器行为等），MUST 编写最小可复现代码（如临时 crate）实测；NEVER 仅凭记忆、推理或搜索得出结论。
- 涉及 `sdk.rs`、`core/`、`plugin_framework/`、`commands/` 的改动，MUST 跑 `cargo check` 零错误后再交付（APPEND_SYSTEM 已要求任何 `.rs` 改动后执行）。
