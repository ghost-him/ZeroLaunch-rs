# 审查报告模板

> 本文件规定 code-review skill 最终报告的结构与输出风格。主 agent 在完成冲突检测后，按此模板生成报告。

## 设计原则

- **最终报告只呈现「问题」本身**：每条问题条目包含四要素——**等级 / 现象 / 位置 / 修复建议**
- 过程性内容（证据、影响、变更前/后、规则原文、判定依据等 agent 分析过程的产物）**不进入最终报告**；这些字段保留在子 agent 报告中，仅作为主 agent 冲突复核的依据
- **来源标注必须保留**：用于核对「每个子 agent 的问题都如实全量呈现」，不得因报告已长或与其他 agent 重复而省略任何子 agent 的发现
- 冲突复核行内化：挂在对应问题条目下追加一行，不设独立章节
- 大 commit 下钻的新发现并入问题清单对应分组，标注 `[下钻]`，不设独立章节

---

## 报告结构

按以下顺序输出。各节无内容时写"无"。

### 一、总览

| 项目 | 内容 |
|------|------|
| **结论** | `通过` / `建议修改后合并` / `阻塞合并` |
| **变更概要** | 一句话（聚合视角；跨 commit 时按主要 commit 或子系统概述） |
| **阻塞** | N 项 |
| **高** | N 项 |
| **中** | N 项 |
| **低** | N 项 |
| **疑点** | N 项 |
| **既有问题** | N 项 |

> 若阻塞合并，在表格后加一行注明阻塞的核心原因（1 句话）。

---

### 二、阻塞项

> 必须解决才能合并。按关注点分以下子分组：逻辑 / 回归 / 架构合规 / 规则违反(A 类)。各组内按严重程度降序排列。无内容的子分组整段省略。

#### 逻辑

- **[阻塞]** `文件:行` — 现象
  - 建议：最小修复方向
  - 来源：Agent 2
  - [冲突复核：...]（如有则追加此行）

#### 回归

- **[阻塞]** `文件:行` — 现象
  - 建议：最小修复方向
  - 来源：Agent 3
  - [冲突复核：...]（如有）

#### 架构合规

- **[阻塞]** `[P3]` `文件:行` — 现象
  - 建议：最小修复方向
  - 来源：Agent 4a
  - [冲突复核：...]（如有）

#### 规则违反（A 类）

- **[阻塞]** `[A 类]` `文件:行` — 现象
  - 建议：最小修复方向
  - 来源：Agent 5
  - [冲突复核：...]（如有）

### 四、低优先级

> 含 Agent 4b 的过度设计发现（设计债，标注 `[设计债]`）。格式同「阻塞项」，严重程度为 `[低]`。

---

### 五、疑点与既有问题

> 信息性，不影响合并决策，但需知情。按维度（逻辑 / 回归 / 架构 / 规则）分组，四要素格式。

#### 疑点但证据不足

- **[维度]** `文件:行` — 现象 | 建议

#### 既有问题（非本次引入）

- **[维度]** `文件:行` — 现象 | 建议

---

### 六、规则更新建议（B 类）

> B 类 = 规则已过时，需更新规则。来源：Agent 5。

- `规则文件` — 现象 | 建议更新方向

无则写"无"。

---

## 输出风格

- 每条问题只出现一次，不跨节重复；同一位置的多 agent 同质问题合并为一条并标注全部来源（如 `来源：Agent 2、Agent 4a`）
- 每条问题严格四要素 + 来源标注 + 冲突复核行，不附加其他字段
- 空节写"无"；各节间用 `---` 分隔

---

## 报告文件头部元数据

写入文件时，文件开头加一行：

```
<!-- 审查日期: YYYY-MM-DD | 范围: <范围> | 结论: <通过/建议修改/阻塞> -->
```

文件末尾追加覆盖核对行（如实全量呈现纪律的落点）：

```
<!-- 覆盖核对: 各子 agent 报告的发现已全部纳入，无省略 -->
<!-- 核对明细: Agent 1 (N) / Agent 2 (N) / Agent 3 (N) / Agent 4a (N) / Agent 4b (N) / Agent 5 (N) -->
```
