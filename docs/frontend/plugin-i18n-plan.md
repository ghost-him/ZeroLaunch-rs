# 插件翻译加载方案（优化方向）

> 状态：待实施。本文仅记录背景、现状与未来目标，不涉及具体加载机制的详细设计。

## 背景

- 内置插件（如翻译面板）的用户可见文本此前硬编码中文，违反 i18n 规范，已修复：插件 UI 文本统一使用 `translator.*` 命名空间（见 `src-ui/i18n/locales/{en,zh-Hans}.json`）。
- 目前插件文本与软件本体翻译混在同一个 JSON 文件中，靠命名空间前缀人工隔离，插件无法独立维护自己的翻译。
- 后端 schema 的字段标签（如 `SchemaBuilder::select("llm_vendor", "厂商预设", ...)`）同样硬编码中文，schema 驱动表单渲染后无法随界面语言切换；前端厂商预设的持久化值（`llm_vendor`）也与后端枚举绑定，无法独立本地化。

## 现状

- 前端 i18n 为单一 `src-ui/i18n/locales/{en,zh-Hans}.json`，启动时由 `createI18n` 一次性加载（`src-ui/i18n/index.ts`），切换语言只切换现有 key 的取值。
- 插件翻译与软件本体翻译共存于同一资源文件：新增插件文本需要人工同步修改两个语言文件，且与插件自身打包/分发无关；第三方插件完全没有前端 i18n 入口。
- 插件面板/设置组件引用翻译时直接写 `translator.xxx` key，命名空间约定靠自觉，无机制保证冲突或遗漏。

## 目标

1. 插件独立携带自己的翻译资源（语言 key → 各语言文本），随插件一起分发，不写入软件本体的语言文件。
2. 程序加载插件时，自动将该插件的翻译与软件本体翻译合并（同一 vue-i18n 实例），按当前 locale 生效，切换语言无需重启。
3. 插件命名空间与本体命名空间互不冲突、可独立升级；插件翻译缺失时回退到本体默认或该插件提供的兜底语言。
4. （可选延伸）后端 schema 标签通过插件提供的翻译资源本地化，使 schema 驱动表单也随界面语言切换；`llm_vendor` 等持久化枚举值可迁移为稳定 ID，展示文案与存储值解耦。
